# `zero-to-commit` — 안내

사람이 읽는 문서다. 실행 중 적재되지 않는다 — 실행은 `SKILL.md`가 담당하고, `review-fix:` / `no-commit:` 경로에서는 `paths.md`도 함께 적재된다.
English: `GUIDE.md` — 동일 내용; 한쪽을 고치면 다른 쪽도 고칠 것.

## 무엇인가

작업 한 조각(slice)을 도는 오케스트레이션 루프로, 복잡한 엔지니어링에서 메인 세션 토큰을 최소로
쓰는 것이 목적이다. 메인 세션은 사용자와 함께 청사진 초안을 쓰고, 그 뒤로는 구현도 리뷰도 하지
않는다 — 프리셋 사이를 중계하고, 라운드당 한 번의 웜 빌드를 돌리고, 판정한다. 무거운 추론은
범위가 좁혀진 프리셋에서, 그 표면을 감당할 수 있는 가장 싼 모델로 돈다. 모든 인계는 세션
스크래치패드의 **파일**이다.

## 호출

`/zero-to-commit <플래그> <슬라이스>` 또는 `/ztc <플래그> <슬라이스>` — 어느 쪽이든 같은 실행이다.
`/ztc` 는 `commands/` 에 든 한 줄짜리 명령으로, 스킬과 함께 설치한다(`agents/README.md`). 설치하지
않으면 전체 이름만 인식된다.

## 파이프라인

| 단계 | 프리셋 | 산출물 |
|---|---|---|
| 1 | *(사용자 + 조정자)*, 그다음 `architect` | `blueprint-draft.md` — 슬라이스에 맞는 형태로 쓴 사용자의 결정: 파일·seam·자료구조·오류 처리·비목표; 그다음 `blueprint.md` — architect 의 정제: 인용 결정 ID·시험 계획·패키지·결합, 그리고 설계 변경 제안은 사용자에게 되돌아가는 변경 목록 |
| 2 | `implementer` | 코드 + 단위시험. 자기 트리에서 자기 타깃만 빌드하고 자기가 쓴 시험 바이너리를 직접 돌려 자체 점검한다(configure·clean·`all`·`ctest` 금지) — 증거가 되는 빌드·시험은 조정자가 라운드당 1회 웜 빌드로 한다 |
| 3 | `logic-auditor` (+ `docs-conformance`) | `findings-r<n>.md` — ID 붙은 결함과 실패 시나리오 |
| 4 | `architect` | `dispositions-r<n>.md` — 전 ID 를 fix / defer / invalid 로 판정 |
| 5 | *(커밋 의식)* | 트래커 먼저, 게이트 1회, 그다음 커밋 — 스킬에 내장. 프로젝트에 자체 마무리 스킬이 있으면 그쪽에 위임 |
| 6 | `gatekeeper` | 검사별 pass/fail. 주장이 아니라 디스크와 git 을 본다 |

2~4 가 루프다. 5~6 은 한 번만 돈다.

## 플래그

| 플래그 | 효과 |
|---|---|
| *(없음)* | 1단계부터 전 경로 |
| `simple:` | 청사진 생략, 구현자 단일, finding 판정은 조정자가 직접. 감사자·gatekeeper 는 그대로 |
| `review-fix:` | MR 피드백 경로. 1~2단계를 fetch-and-disposition 으로 대체 |
| `opus-architect:` | 청사진 리뷰와 판정을 `architect`(fable-5) 대신 `architect-v2`(opus)로 |
| `no-commit:` | 검증은 전부, git 쓰기는 없음 — 트래커·커밋 메시지는 스크래치패드 초안으로. gatekeeper 는 커밋 형태 검사를 N/A 처리. `review-fix:` 와 병용 불가 |

플래그 대신 산문으로 지시해도 받는다 — 어느 플래그로 읽었는지 한 줄로 밝힌다.

## 규칙

### 설계는 사용자가 소유하고, 기계적 부분은 architect 가 소유한다

- 청사진 초안은 사용자와 조정자가 함께, 슬라이스에 맞는 형태로 쓴다 — 정해진 템플릿은 없다 —
  그리고 어떤 에이전트를 띄우기 전에 `blueprint-draft.md` 로 저장해서, architect 가 사용자가 본
  바로 그 글을 리뷰하게 한다. 문서가 정해 주지 않는 질문은 리뷰를 띄우기 전에 전부 사용자에게
  묻는다.
- architect 는 초안을 **리뷰**한다. 보고는 항상 두 갈래다: 스스로 적용하는 **정제**(결정 ID 인용,
  불변식 검사, 시험 계획, 패키지 분할, 결합, 구현자가 그대로 실행할 수 있는 문장)와 제안만 할 수
  있는 **설계 변경**(다른 seam, 비목표 변경, 범위 변경, SSOT 와의 모순). 제안된 변경은 사용자에게
  가고, 판정은 같은 architect 에게 돌아간다. 설계 갈래의 어떤 것도 말없이 수용되지 않는다.
- 이 분리는 오리엔테이션 비용을 설계에서 검증으로 옮기고, 사용자가 책임질 수 있는 청사진을
  남긴다. 세션 안에서만 사는 에이전트가 쓴 설계는 세션이 끝나면 주인이 없다.

### 리뷰 범위는 단조적으로 좁아진다

- **1차** 패스가 슬라이스 전체의 표면·관점을 확정한다. **그것이 놓친 관점까지 포함해서** 확정된다.
- **델타** 패스의 질문은 하나다: 판정된 피드백이 제대로 반영됐나. finding 으로 받는 것은 선행
  finding 이 실제로 안 닫힌 경우뿐이다 — 수정이 틀렸거나·불완전하거나·시험이 주장한 것을 고정하지
  못하는 경우.
- 1차가 안 잡은 관점은 열 수 없다. **수정이 새로 쓴 줄에 대해서도** 마찬가지다. 그 외에 눈에 띈
  것은 이 루프에서 고치지 않고 트래커 잔여로 적는다.
- **구현자는 몇 번이든 돌아도 된다.** 커지면 안 되는 것은 리뷰어의 범위다.

### 주석은 finding 이 아니다 — 양방향 모두

- **낡거나 틀린 주석**(드리프트): 감사자는 번호도 심각도도 없이 말미 "comment sweep" 한 묶음으로만
  나열한다. 델타 패스를 유발하지 않는다.
- **없거나 "부족한" 주석**: 아예 보고 대상이 아니다. 코드에 설명이 필요하면 finding 은 코드 자체다 —
  이름·추출·타입 — "주석을 달라" 가 아니다.
- 루프 안에서 주석은 줄거나 사라지기만 하고, 어떤 판정도 주석을 키울 수 없다. 코드는 스스로
  설명하고, 주석은 코드가 말할 수 없는 것 한 줄, 나머지는 전부 문서 디렉터리로 — 문서 파일
  하나하나도 간결하게.

### 표면 하나에 리뷰어 하나

- 같은 표면에 리뷰어 둘을 붙이지 않는다.
- 표면이 겹치지 않으면 동시 실행해도 된다 — `logic-auditor`=코드, `docs-conformance`=SSOT/ICD/트래커.
- 보조 감사(저장소에 `agy` 프리셋이 있으면 그것, 없으면 새 `logic-auditor` 실행)는
  **분쟁 판정용 타이브레이커**다. 사후에만 부른다.

## 운용 메모

- **리뷰어와 architect 는 이름 없이 띄운다** — 이름 붙인 팀메이트가 아니라 순수 백그라운드
  에이전트로. 이어서 부릴 때는 `SendMessage` 로 그 id 에 보낸다.
- **그 회차에 띄운 리뷰어가 전부 보고해야 회차가 닫힌다.** 리뷰어가 하나라도 미결이면 게이트를
  시작하지 않는다.
- **리뷰 대기 시간을 쓰되, finding 에 좌우되지 않는 것만 미리 쓴다.** 트래커의 기계적 항목·회신
  골격·이미 검증된 수정의 커밋 메시지는 미리 써도 된다. mutation 목록처럼 finding 에 좌우되는
  글은 미리 쓰지 않는다 — 미검증 표시를 달아 두고 finding 이 오면 대조한다.
- **구현자는 빌드하고 돌려서 자체 점검하고, 증거가 되는 빌드·시험은 조정자가 라운드당 1회 한다.**
  구현자는 자기가 띄워진 트리에서(병렬 라운드면 자기 worktree, 혼자면 라이브 트리) 자기 파일이
  속한 타깃만 증분 빌드하고, 자기가 쓴 시험 바이너리를 직접 돌리며, 파일 단위 게이트(포매터·
  복잡도·저장소가 요구하는 모든 컴파일러)를 돌린다 — configure·clean·`all`·`ctest` 는 금지.
  예전의 일괄 빌드 금지는 공유 빌드 디렉터리 경합을 막기 위한 것이었고 worktree 격리가 그 경합을
  없앴다; 남은 것은 실행되지 않은 시험이라는 비용뿐이었다(2026-09-07: 한 수정 라운드의 결함
  7건 중 4건이 구현자가 볼 수 없었던 빌드·실행 시점 실패). 조정자는 기존 빌드 트리에서 증분
  빌드하고(루프 안에서 clean·재구성 금지), 새 코드에 대해 저장소의 함수 단위 정적 검사를 이
  시점에 함께 돌린다. 실패는 한 묶음으로 **같은** 구현자 에이전트에 SendMessage 로 회송한다 —
  새로 띄우면 직전 실수를 모르니 되풀이한다. 묶음당 재빌드 1회 — 같은 실패가 세 번 왕복하면
  사용자에게 올리고, 같은 게이트가 다른 줄에서 두 번 실패하면 구현자가 모르는 규칙이니 다음
  묶음 전에 브리프에 적어 넣는다. 주석만 고친 변경은 빌드 자체가 필요 없다.
- **병렬 구현자는 worktree 로 격리한다.** PARALLEL-SAFE 패키지는 보통 파일 단위로 서로 겹치지
  않지만, 패키지들이 (선언부·구현체·시험처럼) 다른 축으로 나뉘면서 파일 하나를 공유할 때는
  청사진이 그 파일 안의 겹치지 않는 append-only 구간으로 대신 나눠 줄 수 있다. 어느 쪽이든 병렬
  구현자는 각각 `isolation: 'worktree'` 로 띄우고, 조정자가 각 worktree 의 변경을(구간 소유
  패키지는 해당 구간에만) 라운드의 단일 웜 빌드 전에 실제 트리로 병합한다. worktree 당 콜드
  구성이 드는 대신, 라운드 자체의 빌드 지점은 여전히 하나의 웜 증분 빌드로 남는다.
- **자르는 지점은 결합(coupling) 경계지, 커밋 경계가 아니다.** 결합은 병렬 안전성과 다른 질문이다 —
  두 패키지 사이 이음매에 결함이 살 수 있으면 결합된 것이고, 파일이 겹치지 않으면서 결합된 경우도
  흔하다. 결합된 패키지는 한 리뷰 범위·한 루프에 함께 둔다. 형제 패키지가 생기기 전에 하나를
  커밋하면, 그 이음매의 양쪽을 동시에 쥔 리뷰어가 아무도 없게 된다.
- **에이전트 하나의 작업량은 두 경계 사이에 둔다.** 도구 호출 60회 분량을 상한으로 삼되(에이전트
  비용은 호출 수를 따라간다), 실행당 오리엔테이션 하한 ~80~120k 밑으로는 쪼개지 않는다. 브리프는
  산출물을 가리키기만 하고 옮겨 적지 않는다.
- **리뷰 진행 중인 리뷰어에게 메시지를 보내지 않는다.** 보고를 보강하는 게 아니라 처음부터 다시
  쓰게 만든다. 필요한 것은 전부 실행 브리프에 넣고(그 회차의 diff 도 미리 스크래치패드에 써서
  경로로 넘긴다), 정정은 델타 브리프까지 기다린다.
- **증거 실행 전에 모든 편집을 끝낸다.** 게이트 로그는 그 시점 트리에 대한 증거다. 이후에 트래커
  한 줄만 고쳐도 모든 로그가 무효가 된다. 게이트가 무엇인지에 대한 권위는 목록이 아니라 시험
  러너다 — `-R` 부분 실행이 아니라 전체 스위트를 돌린다.
- **에이전트 주장은 소스로 확인한 뒤 움직인다** — 양방향으로: 결함을 깨끗하다고 한 경우와, 깨끗한
  줄을 결함이라고 한 경우 둘 다. 인용하는 수치는 전부 로그에서 읽는다. 기억에서 쓰지 않는다.

## 비용

전 경로 실행 2회 실측: **서브에이전트 토큰 ~2.9~3.0M, 벽시계 135~170분, 서로 다른 에이전트 14개**,
각각 ~30개 파일 / ~4,000줄 추가. 토큰 분포는 구현자 ~52%, 리뷰어 ~31%, architect ~7%,
gatekeeper ~4%.

핵심 형태:

- **에이전트 비용은 도구 호출 수만 따라간다.** 매 호출이 누적 문맥 전체를 다시 보내므로 한
  에이전트 안의 비용은 `1+2+…+n` 으로 자라고, 호출당 단가는 2~4k 로 평평하다. 작업량 상한이
  유일한 실질적 토큰 지렛대다.
- **실행 하나마다 오리엔테이션 하한 ~80~120k 를 낸다** — 작업 크기와 무관하게. 파일 2개짜리
  수정도 79k 였다. 판정·finding·대상 파일·주변 관례를 어차피 읽어야 하기 때문이다. 이 하한
  아래로 쪼개면 고정비만 곱해진다.
- **서브에이전트는 실행 사이에 이미 문맥이 비워진다.** 그러니 더 자주 비우는 것은 정작 토큰이
  쓰이는 곳에 도움이 안 된다. 슬라이스를 잘게 쪼개 커밋하면 커밋 준비 지점마다 게이트 실행과
  gatekeeper 패스가 붙어 오히려 더 비싸지고, 이음매 결함까지 흘려보낸다.

중간 규모 슬라이스 벽시계 기준: 구현+빌드 회차당 20~30분, `logic-auditor` 10~20분(xhigh 기준
측정, 현재 프리셋은 high), `docs-conformance`·`gatekeeper` 각 5분 안팎. 예상을 넘기는 원인은
대개 finding 물량과 사용자 결정 대기다 — 낭비가 아니라 정확성 작업이다.
